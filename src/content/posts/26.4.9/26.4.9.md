在 Redis 的源码实现中，`redisDb` 是存储数据的核心容器。Redis 服务器默认会初始化 `16` 个这样的逻辑数据库，每个数据库都维护着自己的键空间、过期信息以及一些运行时状态。

```c
typedef struct redisDb {
    dict *dict;                 /* 数据库键值对字典，保存所有键值对 */
    dict *expires;              /* 保存设置了过期时间的键及其过期时间（毫秒时间戳） */
    dict *blocking_keys;        /* 处于阻塞状态的键（例如 BLPOP） */
    dict *ready_keys;           /* 解除阻塞状态的键 */
    dict *watched_keys;         /* 被 WATCH 命令监视的键（用于事务） */
    int id;                     /* 数据库 ID */
    long long avg_ttl;          /* 数据库内键的平均存活时间（用于统计） */
    unsigned long expires_cursor; /* 过期键循环处理的游标 */
    list *defrag_later;         /* 等待进行碎片整理的键列表 */
} redisDb;
```

其中，与过期策略最直接相关的是两个哈希字典：

- `dict` 用来保存数据库中的键值对本身，也就是实际的数据内容。
- `expires` 用来保存“哪些键设置了过期时间”以及“它们会在什么时候过期”。这里记录的值通常是毫秒级时间戳。

这种设计的好处在于，Redis 不需要把“值对象”和“过期时间”强行绑在同一个结构里，而是把过期信息单独维护。这样一来，只有设置了过期时间的键才会出现在 `expires` 字典中，普通键不会额外承担这部分管理成本。

在 Redis 中，我们经常会给某些数据设置过期时间。一个键过期之后，并不意味着 Redis 会立刻为它单独创建一个定时器去删除它；如果为大量键都维护独立定时任务，会带来明显的调度开销，也会影响 Redis 的整体处理效率。

那么，Redis 是如何在保证性能的前提下完成过期数据清理的呢？核心思路是避免把删除操作完全交给实时定时器，而是通过两种主要策略配合完成过期键回收。

## 惰性删除
当我们为一个键设置 `TTL` 时，Redis 会同时在当前 `redisDb` 的两张字典中记录信息：

- 在 `dict` 中保存真正的键值对；
- 在 `expires` 中保存这个键对应的过期时间。

需要注意的是，`dict` 和 `expires` 虽然都以同一个键作为索引，但它们是两张独立的哈希表，Redis 只是分别通过同一个键去查找对应的数据和过期时间，并不是简单地共享同一个桶位置。

所谓惰性删除，本质上就是“访问时检查”。当客户端对某个键执行读取、写入、删除或其他相关操作时，Redis 会先判断这个键是否已经过期：

- 如果已经过期，就先执行过期删除，把它从键空间中清理掉；
- 如果还没有过期，再继续执行后续操作，并返回对应结果。

因此，惰性删除并不会主动扫描所有过期键，而是只在这个键再次被访问时，才顺带完成过期检查和清理。这种方式的优点是实现简单，而且不会为没有被访问的键额外付出检查成本；缺点是如果某些过期键长期不再被访问，它们仍然会继续占用内存。


## 周期删除
如果说惰性删除解决的是“被访问到的过期键”，那么周期删除解决的就是“长期没有被访问、但已经过期的键”。它的核心思路不是实时追踪每一个键，而是由 Redis 在后台以固定节奏抽样检查一部分设置了过期时间的键，并把其中已经过期的键删除掉。

在 Redis 中，周期删除主要有两种触发时机：

- `serverCron` 会按照 `server.hz` 的频率定期执行过期键处理，这通常可以理解为较常规的后台清理过程；
- 在事件循环进入休眠前，Redis 还会在 `beforeSleep()` 阶段再做一次更快速的过期键处理，用来加快过期键回收。

需要注意的是，这里的核心并不是“定时把所有键都扫描一遍”，而是“周期性地抽样一部分过期字典中的键”。这样做的原因很直接：如果每次都全量扫描所有设置了过期时间的键，代价会过高；而抽样删除虽然不是绝对实时，但能在内存占用和 CPU 开销之间取得更好的平衡。

### SLOW 模式

`SLOW` 模式由 Redis 的时间事件 `serverCron` 触发。它会按照 `server.hz` 的频率周期性执行；在默认配置下，`hz` 通常是 `10`，也就是每秒触发 `10` 次。

这个模式最关键的特点，是它有明确的时间预算限制。Redis 不会让一次过期扫描无限执行下去，而是只在给定的时间片内做清理；默认配置下，这个时间预算通常可以近似理解为单次不超过约 `25ms`。一旦本轮扫描耗时超过阈值，Redis 就会立刻停止，把剩余工作留到下一次 `serverCron` 再继续处理。

在一次 `SLOW` 模式的过期清理中，Redis 会按数据库依次推进。对于每个 `redisDb`，它会执行如下过程：

1. 从当前数据库的 `expires` 字典中随机抽样一小批键，默认每轮抽取 `20` 个；
2. 逐个检查这些键是否已经过期；
3. 对已经过期的键执行删除；
4. 统计这一批样本中“过期键”的比例。

这里还有一个重要的继续条件：如果这一轮抽样里，过期键比例仍然比较高，那么说明当前数据库中可能还积压着大量过期键，Redis 就会立刻继续下一轮抽样检查。默认情况下，这个阈值是 `25%`，也就是抽取的 `20` 个键里如果有超过 `5` 个已经过期，就说明还有必要继续清理。

因此，`SLOW` 模式并不是“每次只扫固定 20 个就结束”，而是“只要时间预算还够，并且样本中过期键比例仍然偏高，就继续抽样和删除”。只有在以下两种情况下，它才会结束本轮清理：

- 当前这一轮抽样的 `20` 个键里，过期键数量不超过 `5` 个，也就是过期比例不再高于 `25%`；
- 本次扫描的累计耗时已经达到时间预算上限，默认配置下通常可近似理解为约 `25ms`。

如果是因为时间预算耗尽而中断，Redis 会保留当前的推进位置，在下一次 `serverCron` 触发时继续向后处理。这样做的目的，就是把过期键清理拆散到多个时间片里完成，避免一次性扫描过久而阻塞主线程。

### FAST 模式

如果说 `SLOW` 模式更像常规的后台清理，那么 `FAST` 模式就是 Redis 在事件循环“空档期”里做的一次快速补扫。它不是按照固定时间片独立调度，而是在 `beforeSleep()` 阶段触发，也就是 Redis 处理完一轮事件、准备进入阻塞等待新的网络 `IO` 之前，顺手再做一次较短的过期键检查。

也正因为它发生在事件循环的尾部，`FAST` 模式的触发频率通常会高于 `SLOW` 模式；但与此同时，它对自己的约束也更严格，目的是尽量不影响正常命令处理。

在默认配置下，`FAST` 模式主要有三层限制：

- 单次执行时间上限通常是 `1ms`；
- 距离上一次 `FAST` 执行时间太近时，会直接跳过，默认可近似理解为至少间隔 `2ms`；
- 如果上一轮慢速扫描并没有表现出明显的“过期键积压”，那么这次快速扫描也可能根本不启动。

换句话说，`FAST` 模式并不是“每次事件循环都一定执行”，而是“只有在值得快速补扫时才执行”。这样可以避免它在事件循环中被过于频繁地触发，反而拖慢主线程。

从底层实现上看，`FAST` 和 `SLOW` 共用同一套主动过期删除逻辑，只是传入的运行参数不同。因此它的基本流程和 `SLOW` 模式非常接近：

1. 从上一次处理到的数据库位置继续推进；
2. 在当前数据库的 `expires` 字典中随机抽样一批键，默认仍然是 `20` 个；
3. 检查这些键是否过期，并删除已经过期的键；
4. 根据当前样本中过期键的比例，决定是否继续下一轮抽样。

不过，`FAST` 模式比 `SLOW` 模式要克制得多。默认情况下，只有在以下条件同时满足时，它才可能继续做下一轮抽样：

- 当前样本中过期键比例仍然较高；
- 总耗时还没有达到 `1ms` 的时间上限；
- 本次快速循环本身没有因为前置限制而被直接跳过。

一旦达到时间上限，或者快速扫描已经没有足够收益，`FAST` 模式就会立刻退出，把主线程尽快交还给正常的事件处理流程。也正因为有 `FAST` 模式的补充，Redis 在两次 `serverCron` 之间，仍然有机会更及时地回收一部分过期键。
